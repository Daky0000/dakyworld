1. Agent System Architecture

1.1 Conceptual Model

1.2 Core Principles

  • Event-Driven: Orchestrator listens to database changes and webhooks, triggers agents reactively
  • Modular: Each agent is independent; can be enabled/disabled, updated, or replaced without affecting others
  • Customizable: Tools can be assigned/revoked per sub-agent; custom prompts override defaults
  • Reliable: Retry logic, dead-letter queues, dry-run mode for risky operations
  • Transparent: Every action logged immutably; audit trail for compliance and debugging
  • Cost-Aware: Every tool call tracked with cost; prevents runaway API spend

2.1 Sub-Agent Patterns

Decision Makers (AI-Powered)

Use Claude Opus 5 for reasoning, categorization, and content generation:

  • Lead Scorer: Analyzes lead data, assigns likelihood-to-convert score
  • Email Drafter: Writes contextual follow-ups per recipient from their record
  • Proposal Writer: Generates proposals from company audit findings
  • Churn Risk Scorer: Evaluates care plan likelihood to cancel
  • Upsell Detector: Identifies service gaps and upsell opportunities

Executors (Scripted, High-Reliability)

Deterministic workflows with predefined rules:

  • Stripe Charger: Call payment API with validated input
  • Calendar Block: Reserve team member time in project
  • Invoice Generator: Render PDF, compute line items, record in database
  • Email Sender: Dispatch via SMTP with logging

Monitors (Event-Driven)

Watch for state changes, trigger next step:

  • Invoice Paid Detector: Stripe webhook → mark paid, update project status
  • Sequence Completion Detector: All steps sent → mark complete, log results

  • Fallback strategies if a tool fails

4. Orchestrator Architecture

4.1 Responsibilities

  • Route events to the right agent based on event type
  • Manage task flow — create tasks, track status, handle completion
  • Error handling — retry transient failures, escalate permanent errors
  • Audit logging — every action recorded with input, output, cost, duration
  • Rate limiting — global rate limits per tool, per agent
  • Cost management — track API spend, alert if over budget
  • Dry-run mode — preview agent actions before execution (for billing/email)

4.2 Event Types

The orchestrator listens to these event triggers:

Lead Events

  • lead.created — new lead from scraper, import, or manual entry
  • lead.scored — score changed, triggers re-routing
  • lead.statusChanged — stage moved in pipeline
  • lead.sequenceEnrolled — added to email sequence

Proposal & Invoicing Events

  • proposal.created — new proposal drafted
  • proposal.sent — emailed to lead
  • proposal.accepted — lead said yes → auto-create project
  • invoice.created — new invoice for project or care plan
  • invoice.sent — emailed to client
  • invoice.dueToday — 1 day before due date
  • invoice.paid — Stripe webhook confirmed payment

Project & Delivery Events

  • project.created — from accepted proposal
  • milestone.dueToday — 1 day before milestone due
  • task.assigned — assigned to team member
  • timeEntry.logged — team member reports hours

Care Plan Events

  • carePlan.billingDay — monthly billing trigger
  • carePlan.hoursOverage — hours exceeded included allowance

System Events

  • scheduler.hourly — runs every hour
  • scheduler.daily — runs at 00:00 UTC every day
  • scheduler.weekly — runs every Monday at 00:00 UTC

4.3 Task Flow

Event occurs
    ↓
Orchestrator detects event
    ↓
Lookup which agent class handles this event
    ↓
Create AgentTask record (pending)
    ↓
Queue task for execution
    ↓
[Agent starts] — Load sub-agents and their tools
    ↓
Execute sub-agent with available tools
    ↓
[On success] → Record output, mark completed, log cost
    ↓
[On failure] → Log error, check retry policy
    ↓
[If retryable] → Exponential backoff, re-queue
    ↓
[If permanent error] → Move to dead-letter queue, alert owner

5. Agent Management UI (/agents)

The Agent Management Dashboard is the control center for all agent operations. Four main sections:

5.1 Agent Dashboard

Live status overview of all agents and recent activity:

  • System Health: % success rate, avg latency, agents running
  • Recent Tasks: Last 50 agent executions with status, duration, cost
  • Event Queue: Tasks waiting to run (pending, retrying)
  • Alerts: Agents over budget, high error rate, missed SLAs
  • Filters: By agent, status, date range, cost threshold

5.2 Agent Configuration

Customize how agents behave:

  • Enable/Disable: Toggle each agent class on/off
  • Tool Assignments: Matrix showing which tools each sub-agent has access to
  • AI Model: Choose between Claude Opus 5, Opus 4, or Haiku
  • Custom Prompt: Override default system prompt for an agent
  • Rate Limits: Max executions per minute
  • Cost Caps: Daily and monthly spend limits
  • Retry Policy: immediate, exponential backoff, or never
  • Dry-Run Mode: Preview agent actions before execution

5.3 Tool Management

Monitor and configure individual tools:

  • Tool Status: Available, configured, error, unconfigured
  • Credentials: Check if API keys are set, test connectivity
  • Usage Metrics: Calls/day, avg latency, error rate, cost
  • Agents Using: Which agents have this tool assigned
  • Rate Limit: Global cap per minute
  • Last Activity: Last successful call, last error, timestamp

5.4 Logs & Audit Trail

Searchable, detailed log of every agent execution:

  • Columns: Timestamp, Agent, Sub-Agent, Event Type, Status, Duration, Cost, Error
  • Expand Row: View full input/output JSON, tool calls, error stack
  • Filters: Agent class, sub-agent, event type, status, date range, cost threshold
  • Export: CSV or JSON for external analysis

5.5 Runbooks (Pre-Built Workflows)

Click to execute multi-agent workflows manually:

  • Manual Lead Nurture: Score all leads matching criteria, enroll in sequence, send first email
  • Project Completion: Mark project done, generate final invoice, send completion email to client
  • End of Month Reporting: Compute MRR, pipeline, invoices, send to owner
  • Onboard New Care Plan: Create Client, first invoice, add to Slack channel, welcome email

5.6 Role-Based Access Control

PROJECT_MANAGER Project delivery agent logs, project-related events Trigger project-related runbooks Read-only + trigger

6. Database Schema Extensions

6.1 New Models (Prisma)

Agent System Models

Core models for agent orchestration and execution:

  • Agent: Represents an agent class (Lead Orchestrator, Proposal & Invoicing, etc.)
  • SubAgent: Individual sub-agent (Lead Scorer, Email Drafter, etc.)
  • Tool: Available tools (Claude, Stripe, Email, etc.)
  • ToolAssignment: Links sub-agents to tools with permission levels
  • AgentTask: Records every agent execution (input, output, status, cost, error)
  • ToolUsageLog: Tracks cost and usage of each tool call

Client Portal & Team Collaboration

  • ClientPortalUser: Client-facing user accounts (separate from internal Users)
  • Notification: Notifications for both internal users and clients
  • Handoff: Tracks team handoffs (Designer → Developer, etc.)
  • IntegrationMarketplaceItem: Public list of integrations Dakyworld supports

Analytics & Insights

  • DailyMetrics: Daily snapshots of KPIs (leads, proposals, revenue, MRR, hours)
  • ChurnRiskScore: Weekly churn prediction for care plans
  • UpsellOpportunity: Detected service gaps and upsell recommendations
  • CaseStudy: Public case studies with results and metrics

6.2 Schema Changes to Existing Models

Add these fields to existing models:

  • Client: Add clientPortalUsers, churnRisks, upsellOpportunities
  • CarePlan: Add churnRiskScore relation
  • Project: Add handoffs relation for team coordination
  • User: Add notifications relation

8. Six Platform Enhancements Overview

8.1 Enhancement 1: Client Portal

Problem: Clients have no self-service visibility into projects, invoices, or care plans. Each update requires manual communication.

Solution: Dedicated portal with separate authentication. Clients log in to see:

  • Active projects with milestones, deliverables, status
  • Invoices with payment links, due dates, payment history
  • Care plan details: monthly cost, hours included, hours used, renewal date
  • Monthly reports (auto-generated by agents)

Impact: 30-40% reduction in support requests; improves retention; justifies premium pricing.

8.2 Enhancement 2: Team Collaboration Hub

Problem: Handoffs between designers, developers, and operations are informal and error-prone.

Solution: Internal collaboration tool tracking:

  • Handoff board (Pending → Acknowledged → In Progress → Completed)
  • Team capacity calendar (who is allocated to what, % hours booked)
  • Time tracking dashboard (who logged hours, on what, this week)
  • Automated alerts when assigned or handoff awaits acknowledgment

Impact: Fewer missed handoffs, better capacity visibility, improved project delivery time.

8.3 Enhancement 3: Integrations Marketplace Page

Problem: Website mentions we work with many tools, but doesn't list them or explain capabilities.

Solution: Public /integrations.html page showing:

  • Grid of integration cards (Stripe, Google Workspace, WhatsApp, CRM, etc.)
  • Filters by category (email, payment, analytics, communication, design)
  • "Works with Dakyworld" badge system
  • Setup guides and documentation links

Impact: SEO benefits; builds trust; qualifies leads upfront ("we work with Shopify").

8.4 Enhancement 4: AI Analytics Engine

Problem: Owner has no visibility into churn risks or upsell opportunities until it's too late.

Solution: Daily analytics collection + weekly AI analysis:

  • Daily KPI snapshots: leads created/converted, proposals/invoices, MRR, hours, team capacity
  • Churn risk scores for care plans (0-100 scale with reasons)
  • Upsell opportunities (clients on low tier with high hours, service lines not yet purchased)
  • Revenue forecasting (quarterly/annual MRR projection)

Impact: Data-driven growth; catch retention issues 4 weeks early; identify $10k+ upsells.

8.5 Enhancement 5: Notifications System

Problem: Important events (invoice due, care plan renewal, milestone delay) happen silently.

Solution: Multi-channel notification delivery:

  • In-app notifications (bell icon, notification center)
  • Email digests (daily or event-triggered)
  • Slack alerts (#dakyworld channel)
  • User/client controls to opt in/out

Impact: Team stays informed; response time improves; clients feel supported.

8.6 Enhancement 6: Enhanced Case Studies

Problem: Only 3 case studies on website; not enough to build credibility with different verticals.

Solution: Expand to 6-8 detailed case studies with:

  • Industry and service line filters
  • Before/after metrics (time saved, revenue gained, security improved)
  • Client testimonials with video if possible
  • Dedicated landing page (/case-studies) for SEO

Impact: Higher conversion; better SEO; social proof for different buyer personas.

9. Scalability & Future Phases

9.1 Current Architecture (Phase 1)

Deployment: In-process scheduler in Node.js (current)

Strengths:

  • Simple, no external dependencies
  • Proven for current workload (4 scheduled jobs, ~100 leads/day)
  • Fast iteration during MVP

Limitations:

  • Agents block each other (sequential execution)
  • No job persistence across restarts
  • Can't scale beyond single instance

9.2 Phase 1.5: Distributed Agent Execution (Optional)

When: After Phase 4 (when agent load exceeds current capacity)

Upgrade: Replace in-process scheduler with Redis Bull queue

Benefits:

  • Multiple workers run in parallel (5 Email workers, 1 Analytics worker, etc.)
  • Jobs persist in Redis; surviving server crashes
  • Priority queues (invoice > lead scoring)
  • Job retries and exponential backoff built-in
  • Better observability (Bull Dashboard)

Files to add:

  • server/src/queues/agentQueue.ts — Redis queue setup
  • server/src/workers/agentWorker.ts — Worker process
  • Update orchestrator to enqueue instead of execute

9.3 Future Phases (Post-Launch)

10. Architecture Decisions & Assumptions

Decision Chosen Approach Rationale
Agent Hierarchy Orchestrator → Agent Classes → Sub-agents Clear separation of concerns, enables reusability and testing
Tool Abstraction Plugin architecture with standard interface Easy to add/remove tools, test independently, track costs
AI Strategy Hybrid: scripted + AI-powered agents Reliability for critical ops (billing), flexibility for reasoning tasks
Deployment Model In-process first, upgradeable to Redis Bull Faster MVP, proven at current scale, migration path clear
Event Model Database changes + webhooks (polling initially) No external event bus needed; can upgrade to Kafka later
Client Auth Separate email/password from internal User auth Clean separation; can add SSO/OAuth later
Default AI Model Claude Opus 5 for all agents initially Best reasoning; can downgrade to Haiku for cost later
High-Risk Agent Safety Dry-run mode enabled by default for billing/email Prevents accidental charges or spam before ops can review
Cost Tracking Log costs, no enforcement initially Visibility without blocking; owner sets caps after seeing usage
Config Storage Database, not environment variables Allows owner to modify without code redeploy
