What this document is

Dakyworld OS is not a chatbot with a job list. It is a workforce: __AGENTCOUNT__ agents, each with one craft, each with an employee record, a written instruction, a granted toolkit, and a level of autonomy a person set deliberately. This describes the machine that runs them.

__AGENTCOUNT__AgentsOne deliverable each. Nobody does two jobs.
__TOOLCOUNT__Tools__OUTWARD__ reach outside the company; __SPENDING__ spend money.
__LAYERCOUNT__Prompt layersPer agent, editable, and read fresh on every task.
60sThe tickNine independent jobs, settled separately.

There are three documents about this system and they answer three different questions. The Agent Master Workflow answers how does a stranger become a paying client — the business flow, in nine stages. The Dakyworld OS Reference answers what exactly is each agent told — every roster row and every instruction printed in full. This one answers the question underneath both: what actually happens. What runs, in what order, gated by what, recorded where, and stopping for whom.

Everything numbered in it is read out of the code it describes at build time — the roster from services/agentRegistry.ts, the catalogue from services/tools/catalogue.ts, the writing jobs from services/writers/registry.ts, the model routing from lib/models/registry.ts. A reference table that has drifted from the system is worse than no table at all: somebody grants a tool that no longer exists, or looks for one added last month and concludes it cannot be done.

The one sentence that explains the whole design

An agent proposes; the gate decides; a person approves what leaves the building. Every agent in the system seeds at autonomy level 1 with dry run switched on, which means it can research, read, reason, draft and prepare — and nothing it decides takes effect until somebody raises that level or approves that specific action. Everything in Part 02 exists to make that promise true in code rather than in a prompt.

How to read the rest

Parts 01 to 03 are the machine: what an agent is, what it may call, and what happens between a task being raised and a person reading the result. Part 04 is the clock — the part that happens whether or not anybody opens the app, and therefore the part worth being certain about before an autonomy level is raised. Part 05 walks every process the system runs, end to end. Part 06 puts them together into one ordinary day with everything switched on.

Part 01

What an agent is

An employee record, not a naked prompt. A job with one deliverable, a written instruction in ten layers, a toolkit somebody granted, a level of autonomy somebody set, and a memory of what it concluded last time.

In this part The employee record · The one-job rule · The ten instruction layers · The eight regions of an assembled prompt · Memory and context, and why they are not the same thing · The org chart in numbers
01.1

The employee record

Every agent is a row in Agent, seeded from services/agentRegistry.ts and never overwritten by a deploy.

key
The stable identifier the seeds, the event router and the mail room address it by. outreach.writer, billing.collector, review.look.
name & title
What a person calls it. The name on a task card and on the audit PDF.
tier
Board, Executive, Governance, Operational or Specialist. Decides what kind of thing it produces — a decision, or a deliverable.
department
Which part of the business it belongs to. Nine of them.
managerKey
Self-reference by key. This is the delegation graph: an agent may only hand work down to a direct report. A managerKey pointing at nobody silently breaks delegate, which is why a roster check exists for it.
mission
The one thing it exists to produce, in a sentence.
skills
What it is good at, in a client’s words rather than a tool key’s. Read by findAgent, so “who do I ask for a video edit” has an answer.
toolkit
The grant. Tool keys this agent may call. An agent with an empty toolkit can call nothing at all.
autonomyLevel
0 observe · 1 draft · 2 recommend · 3 execute-with-policy · 4 autonomous · 5 delegated. Seeds at 1.
dryRun
Sits above the level: on means nothing it decides takes effect. Seeds on.
prompt
The __LAYERCOUNT__ layered sections. Editable, and promptEditedAt marks a rewritten seed so a deploy cannot undo it.
status
DRAFT, ACTIVE, PAUSED or RETIRED. Pausing an agent is how standing work is stopped; a paused or retired agent is refused at the gate and is not a routing destination.

A deploy never overwrites an edit

ensureAgents() only ever creates. New agents arrive on deploy; re-wording an existing one in the seed file changes nothing on a live database. That is deliberate — a deploy must not undo an edit the founder made to words that go out under his own name — and it has one consequence worth remembering: a tool added to a seed after that agent already exists does not join its grant. Appendix B lists the tools currently in nobody’s toolkit for exactly this reason.

01.2

The one-job rule

No agent does more than one task. Read as one deliverable, one definition of done — not one tool, and not one department.

The test for anything added to the roster: does this produce more than one kind of finished thing? A cold email and a LinkedIn message are one thing in two wrappers. A proposal and an invoice are two things.

It bites harder for agents than for people. An agent holding three jobs has one prompt that must describe all three, one toolkit that is the union of all three, and one memory in which what it concluded about chasing an invoice is recalled while it is writing a proposal. Three separate ways of being worse at each. It also makes the roster answerable: who chases late payments is now a card you can pause or re-prompt without touching how proposals get written.

The board and the executive tier are deliberately not split. Their output is a decision or a brief — one deliverable — even where the scope lists four areas. Splitting those would produce a dozen cards that each recommend a fraction of a judgement.

01.3

The __LAYERCOUNT__ instruction layers

An agent’s prompt is not one block of text. It is __LAYERCOUNT__ named sections, composed in this order, read fresh from the database on every single task.

__LAYERTABLE__

Three places must agree on these names — the API that validates an edit, the runner that composes them, and the screen that draws one box per layer — so there is exactly one list, exported as PROMPT_LAYERS.

An edit lands on the next task, not the next restart

The runner reads the row rather than a cached copy. Change the process layer on the Agents screen at 11:04 and the task that starts at 11:05 runs on the new words. POST /agents/:key/prompt/reset restores a seeded agent’s shipped wording without touching its toolkit, autonomy or dry-run setting.

The trap: an instruction that changes nothing

A prompt layer only governs the work if the work actually reads it. Several deliverables used to be written by string constants no screen displayed and no edit could reach — the founder edited a cold-email prompt and the next cold email came out identical. That is what the writer registry in Part 05 exists to close: every job a model writes now names the agent whose instruction writes it. Before editing a prompt to change an output, check the writer table in 05.10 that the output is actually owned by that agent.

01.4

What an agent is actually told

The assembled prompt has eight labelled regions. Only one of them is authored by a person; the rest are built from live state at the moment the task starts.

1
Its instructions
The __LAYERCOUNT__ layers run together in order — or the founder’s own replacement text, if the prompt has been rewritten. The only editable region.
2
What it is relied on for
Its skills, as a list. Edited on the Agents screen.
3
Who Dakyworld is
The brand block from services/dakyworld.ts. The same for every agent.
4
The company’s details
From Settings → System — one record. Change it there and every agent and every document follows.
5
How it writes
The voice block. Also the same for every agent.
6
What Dakyworld holds
Shared memory recalled for this task’s subjects. Presented as standing instruction: where one conflicts with what the agent would otherwise do, it follows it and says so.
7
What it already knows
Its own memory for the same subjects. Presented as its own conclusions: if the record in front of it contradicts one, the record wins and it must say so.
8
How it works here
Tool etiquette, what a preview means, what to do when refused, and the escalation order. Added only when the agent is holding a task — a colleague being asked a question gets regions 1–7 and not this one, because telling somebody with no tools how to use them is noise.

Regions 6 and 7 are two headings on purpose. They carry different authority, and an agent that argues with a house rule because it was pasted in under the heading “your own conclusions” is a failure of that paragraph rather than a failure of the agent.

The roster is a number, not a list

Region 8 tells an agent it has __AGENTCOUNT__ colleagues without naming any of them. Printing __AGENTCOUNT__ names into every prompt would cost more tokens than most tasks; telling it the number is what makes findAgent the obvious next move instead of a tool it never thinks to reach for.

The escalation order, in the words the agent is given

When work needs a craft that is not its own, the answer is never to attempt it anyway. It works down this list and stops at the first step that answers: 1. findAgent — find whose craft this is, before attempting it. 2. consult — keep the work, ask one question inside their craft. 3. handOff or delegate — the work itself is theirs. 4. needSkill — only when findAgent found nobody. “Asking is cheap and being wrong in public is not.”

01.5

Memory and context are not the same thing

One is what an agent concluded. The other is what happened. Keeping them apart is what lets an agent be told “your own conclusions lose to the record in front of you” and have that mean something.

Memory — AgentMemory

A decision and why, an outcome, something learnt. Written with remember. Two scopes: AGENT is its own and outlives only itself; SHARED has a null agent key, keeps its author, and is recalled by every agent.

Recall is by subject — lead:x, client:y, self — never by similarity. A similarity search would eventually put one client’s facts in another client’s letter. Sharing widens who sees a memory, never when it comes up.

findSecret() refuses credential-shaped content outright, because a memory is re-read into a prompt every time its subject comes up.

Context — the dossier

Everything known about one company, as one document: the audit from WebsiteAudit, the letters from EmailMessage, the calls from Communication, and the notes with no home of their own from ContextNote. Written with addToHistory, read with readHistory.

Assembled at read time, never stored. A fact with two homes eventually has two values — and a log only knows what happened after it was switched on, so every company audited before this shipped would otherwise have an empty dossier, which is exactly when an agent most needs one.

The instruction the agent is given says it plainly: writing an opinion into the history dresses it up as a fact for somebody who was not there; writing an event into your memory keeps it from the colleague who needs it.

Part 02

What an agent may do

__TOOLCOUNT__ tools in __GROUPCOUNT__ groups, one way of calling any of them, and four checks every call passes before the handler ever runs. Adding a tool means one entry in a catalogue; it inherits the whole policy by existing.

In this part The catalogue · The gate, in order · The autonomy ladder · What a preview is · The rationale a spend must carry · The nine built-in tools every agent has · The audit row
02.1

The catalogue

A tool is a catalogue entry: a group, a purpose, what integration it needs, a Zod schema, a handler, and a preview. Two flags decide what it costs to be wrong.

__TOOLCOUNT__Tools in codeAcross __GROUPCOUNT__ groups.
__OUTWARD__OutwardVisible outside the company. Needs level 3.
__SPENDING__SpendingCosts real money. Needs level 4.
+MCPConnected serversAdd more tools, under the same gates.
__GROUPTABLE__

outward and spends are the whole risk model

Everything else in the catalogue is description. Those two booleans decide which autonomy level a call needs, what a rehearsal holds back, what a budget ceiling downgrades, and which calls have to carry a written rationale. A tool author sets them once and never thinks about policy again.

02.2

The gate

invokeTool in services/tools/invoke.ts is the only way a tool gets called. Everything an agent is not allowed to do is enforced here rather than in the tools, in this order.

1
Does the tool exist, and is the integration behind it configured
Readiness. A Slack tool with no Slack connected is refused with a sentence that names the setting, not with “something went wrong”.
2
Is the agent alive, and is it granted this tool
A RETIRED or PAUSED agent is refused outright. The grant is toolkit; an empty toolkit can call nothing.
3
Is it over a hard spending ceiling
Only checked for a tool that spends — a blanket hold would stop an agent reading a record, which blinds it without saving a penny. This is the one check an approval cannot lift: approving a letter is a decision about the letter, not a decision to go over budget. The refusal names the ceiling so it can be raised and the card approved again.
4
Does the autonomy level allow acting, or only preparing
Below level 3 an outward call is downgraded to a preview. Below level 4 a spending call is. This produces dryRun, not an error — because a prepared action a person can approve is the useful outcome.
5
Is the input the shape the tool declared
The Zod schema. A model will confidently pass a string where a date was wanted; this catches it before the handler does something odd with it.
6
Has this exact call already been made
Idempotency. For outward tools the runner passes ${taskId}:${tool}:${sha256(input)}; a successful non-preview call already on record returns its recorded output instead of running again. Opt-in, because two identical sends can be two correct sends — a monthly reminder is the same payload every month. What the runner knows is that a resumed run replaying a turn is always a retry.

Every call is written to ToolCall — including the refusals. That is the record which answers “why did nothing happen last night”.

What an approval lifts, and what it does not

approvedRequestId lifts only the prepare-rather-than-act downgrade. Readiness, the grant and the hard ceiling are all still checked, so a request approved after the tool was revoked, or after the integration was disconnected, is refused rather than honoured. That is what separates it from asOwner, which skips the checks entirely because a person is driving the tool directly.

02.3

The autonomy ladder

Six rungs. Everything on the roster seeds at rung 1 with dry run on, and only a person moves it.

0
Observe
Reads and reports. Calls nothing that writes.
1
Draft
Where everything ships. Researches, reasons and prepares. Outward and spending calls come back as previews, and the task finishes at NEEDS_APPROVAL with the whole thing ready for one decision.
2
Recommend
Writes to our own records and argues for a course of action. Still cannot reach outside the company.
3
Execute with policy
The outward threshold. Sends the email, enrols the sequence, opens the issue, books the meeting, publishes the page. Its policy layer still binds it.
4
Autonomous
The spending threshold. Starts a scrape, raises a payment link, buys a model call it chose to make. Money is the harder mistake to undo, so it is one rung above acting.
5
Delegated
Reserved. Nothing on the roster is set here.

dryRun sits above the level rather than inside it: an agent at rung 4 with dry run on still prepares everything. It is the switch that lets a level be raised for a week and put back without re-editing a card.

A refusal is information, not a failure

When the gate downgrades a call to a preview, the model is told exactly that — in words — and the useful thing then happens: it carries on and prepares the rest of the work instead of stopping. That is why a level-1 agent produces one complete thing to approve rather than five half-finished ones.

The rationale a risky call has to carry

Outward and spending tools take a rationale of three parts — why, gain, risk — and it is required by the schema the model is handed, not by a prompt line that can be forgotten. It is what turns a preview into something a person can actually decide on. “Send this email” is not a question anybody can answer; “send this email, because their certificate expired, which gets us the strongest opening we have, and the risk is that their host caused it” is.

02.4

The nine tools every agent has

These are not in the catalogue and not in any toolkit. They are how an agent relates to the rest of the workforce, and every agent gets them.

 
escalate
Stop and ask. Ends the task at BLOCKED with the question on it. Answering appends to the brief and to the conversation, and the run carries on from where it asked.
 
remember
Keep a decision, an outcome or something learnt, against a subject. Refuses anything credential-shaped.
 
addToHistory
Write to the company’s own account of a client — a call and what was agreed, a decision and what came of it. Every agent that opens the dossier next reads it as evidence.
 
readHistory
The rest of the dossier beyond the headlines the brief carries: the wording of what was sent, what they said back, anything older.
 
findAgent
Search the roster by craft. The first move whenever work is outside its own job.
 
consult
Keep the work, ask a colleague one question inside their craft. They answer from their own instructions and their own memory of this client. Their answer is an opinion, not a checked fact — where it contradicts the record, the record wins and the agent must say so.
 
delegate
Hand work down to a direct report. Constrained by managerKey.
 
handOff
Hand the remaining work sideways to whoever’s craft it is. The brief is written as if to somebody who was not here, because they were not.
 
needSkill
Record that Dakyworld has no such craft — only after findAgent found nobody. Feeds the hiring loop in 05.8. Not a way to put down work that is actually its own; a gap raised for something a colleague already does argues for hiring a duplicate.

Raising work and doing work are deliberately separable

Standing work raises tasks on one tick; the runner works them on the next one. Keeping those apart means you can watch what the workforce decided to start without it having already started.

03.2

The claim

Two ceilings, and the second one is about memory rather than tidiness.

Process ceiling
2 tasks at once across the whole service. One service, one loop, one ceiling.
Agent ceiling
One agent, one task. Enforced inside the claim as a conditional update — agent: { tasks: { none: { status: "RUNNING" } } } — so two processes reaching for the same agent cannot both win.
Rehearsal ceiling
1, below the process ceiling on purpose. A rehearsal is discretionary work and the rest of the business is not.
Run owner
A token identifying this process, stamped on the claim and matched inside every checkpoint write. A process reaped as dead that later wakes finds its token replaced and stops.

The reason for the agent ceiling is worth stating plainly. An agent writes what it concluded as it goes and reads it back on the next task about the same subject. Two tasks about the same lead running side by side interleave those writes, so each recalls half of what the other was in the middle of deciding — and the result is an agent contradicting itself inside one conversation, with nothing in the timeline to show why.

It has one consequence that had to be handled: a stranded RUNNING row now blocks its agent entirely. That is what the reaper in 03.6 is for.

03.3

The loop, turn by turn

A manual tool-use loop, not the SDK’s tool runner — because every call must route through the gate, each call must write its step immediately, and the loop must stop on the agent’s own escalate.

1
Claim
Conditional update to RUNNING, stamped with this process’s token. A STARTED step is written.
2
Gather
Read the agent row fresh. Work out the task’s subjects. Recall memory for those subjects — shared and own, separately. Assemble the dossier headlines into the brief.
3
Compose
The eight prompt regions of 01.4, joined. The tool schemas handed to the model are the agent’s granted toolkit plus the nine built-ins — so a tool it does not hold is not merely refused, it is never offered.
4
Turn
One model call. Anything the agent chose to say on the way is written as a THOUGHT step. Checkpoint written.
5
Call
Each tool the turn asked for, one at a time, through invokeTool. The result is clipped to a size the next turn can carry. Checkpoint written after every single call, so a resume runs only the calls that never happened.
 
The ordering that must not come back
In the tool wrapper, result.dryRun is checked before result.refusedReason. A dry run carries a refusal reason too — the sentence explaining why it was downgraded — so the wrong order files prepared work as refused, leaves the prepared-call count at zero, and finishes the task DONE. The founder then reads “done” about work that never happened.
6
Check the stop flags
Between iterations and between tool calls: has a person asked this task to stop, has the process been told to shut down, has the iteration cap been reached. All three land the run somewhere legible rather than mid-sentence.
7
Repeat, to a ceiling of 16 iterations
The cap counts across resumes. The attempt counter resets on any run that progressed, so the cap catches a task dying in the same place rather than one that met three deploys.
8
Finish
The agent’s final message — what it did, what it found, what a person should do next, in plain English. That message is what gets read. The end state is decided from what actually happened, not from what the agent says happened.

The timeline

Every step is a row in AgentTaskStep, written as the run happens rather than assembled afterwards, so a task in flight can be watched. The kinds are: STARTED THOUGHT TOOL_CALL PREPARED REFUSED DELEGATED CONSULTED and the hand-off kind — the last two distinguished on purpose, because asking a colleague sideways and giving them the work are different events and a timeline that blurs them cannot be audited.

03.4

Checkpoints

A run survives the browser, the deploy and the stop button.

The route that starts a task was always fire-and-forget, so a closed tab never stopped anything. What used to be lost was everything else: a deploy landing mid-task discarded sixteen turns of paid work and began again from the brief.

Written
After every model turn and after every single tool call.
The half-turn
A turn whose calls are only partly done lives outside the message list as pendingAssistant + pendingResults — an assistant turn with only some of its results after it is not a conversation the API will accept. A resume therefore runs only the calls that never happened. That is the entire point: “again” for email.send is a second letter to the same prospect.
Ownership
The run-owner token is matched inside every write.
Heartbeat
Touched on every checkpoint write. Five minutes of silence is a run that has genuinely stopped rather than one that is thinking — generous against the slowest single step, which is one high-effort model turn or one tool call that fetches a site, photographs it twice and waits on Apify.
Kept or cleared
DONE and NEEDS_APPROVAL clear it. BLOCKED, FAILED and CANCELLED keep it — so “carry on” means carry on. Housekeeping prunes the ones nobody was ever going to continue.
03.5

The end states

Six, and each one means something different. Reading them as a set is how you tell a working system from a busy one.

StateWhat it meansWhat to do about it
DONEIt finished and its work took effect.Read the final message.
NEEDS_APPROVALIt finished, and its work was prepared rather than done — the agent was in dry run, or below the autonomy its tools needed. The normal outcome at the shipped settings.Open the approvals queue. Approving re-invokes the tool with the input the schema already validated, so what happens is what was shown.
BLOCKEDIt stopped and asked. The question is on blockedReason.Answer it. The answer must go through the escalation path — onto the conversation as well as onto the brief — or the agent resumes at the moment it asked and asks again.
FAILEDSomething broke, or it was interrupted repeatedly without ever getting further.Read the error. A rate limit is retried up to three attempts before this.
CANCELLEDA person stopped it.Nothing. Its checkpoint is kept.
QUEUEDWaiting for a runner. The normal resting state — and where an interrupted task goes back to, with its place kept.Nothing, unless it has been there a long time: check whether its agent is holding another task.

A RUNNING task can be stopped, but not instantly

An interrupt is a request read between iterations and between tool calls, which returns the task to QUEUED with its place kept. It is not a kill: the loop is not interruptible mid-call, and the route says so rather than lying about it. In testing, three tool calls finish before a poller can even ask — which is why the interrupt harness uses twenty rather than six, and why the first version of it reported false failures for a mechanism it never actually exercised.

03.6

Interrupt, drain, resume, reap

Four mechanisms, all pointed at the same failure: a task left RUNNING by a process that is gone, holding an agent that then cannot work at all.

1
Drain — on SIGTERM
The platform gives a container a few seconds to die politely, and this spends them well: every run in flight is asked to stop at its next safe point, checkpoint written, task back to QUEUED, agent freed. Up to an eight-second grace.
2
Resume — at boot, before the first tick
Runs the last process died in the middle of are handed back before the first tick, because each one is holding an agent that cannot work until it lets go — and each carries a checkpoint, so handing it back costs nothing but the seconds since the restart.
3
Reap — on every tick
A RUNNING row whose heartbeat has been quiet for five minutes, and which no live process in this instance owns, is requeued. Rows this process is actually running are left alone however long they have been going, which is what makes it safe every minute. A run predating the heartbeat is judged on its start time with the old forty-five-minute timeout.
4
Give up — after three attempts without progress
Requeued rather than failed while attempts remain. The counter resets on any run that moved the conversation forward, so this catches a task that keeps dying in the same place — “something is stopping this run rather than it failing” — and not a task that merely met three deploys.

04.2

Two rules every scheduled thing follows

The slot is spent before the work starts

The next due instant is written to the row and advanced before the work begins. A failure therefore cannot be retried in a loop, and a restart cannot fire the same slot twice. Lead capture, care-plan billing and standing work all do this identically.

A missed slot is skipped, not stampeded

Anything more than six hours stale was missed during an outage. It is skipped with a line in the log rather than run six times on boot. Without this, coming back from a long outage would be indistinguishable from a runaway.

Standing work carries a third ceiling of its own: maxOpenTasks per schedule, by default one — so a daily brief that is still unfinished tomorrow does not become two. Combined with the per-agent lock, a loop that raises work faster than an agent finishes it is impossible rather than merely unlikely, which matters because the first sign of that failure would have been the bill.

A DRAFT or PAUSED agent’s standing work is skipped silently. Pausing an agent is exactly how the founder stops its standing work, and a warning every sixty seconds about a deliberate decision is noise.

Capture — how a lead appears

Leads fill themselves. Owner-gated throughout, because runs cost money.

1
A source is configured
One Apify actor, its input, its daily times and its timezone. The Apify token lives encrypted in the database rather than in an environment variable — the whole point is adding a source without a redeploy.
2
The tick finds it due
Slot advanced first. Skipped if more than six hours stale.
3
The cost ceiling is checked
Every shipped template actor is pay-per-event, so an item cap does nothing — a maximum total charge is the cap that works. The budget check fails open if Apify’s usage endpoint is unreachable: a monitoring blip must not stop lead generation.
4
The run starts

05.3

The mail room — what happens to a reply

Somebody answering a cold email is the most time-sensitive event this company produces. The difference between forty seconds and four minutes is the difference between a business that is paying attention and one that is not.

Watchmailbox/watcher.ts

A long-lived connection sitting in IMAP IDLE. It does not read anything — it listens, and asks the sync to do the reading on its own short-lived connection. A socket that is fetching is not idling, and juggling both on one connection is where every home-made IMAP client goes wrong. IDLE is renewed every nine minutes because what kills it is usually a NAT table rather than the server.

Syncmailbox/sync.ts

Reads the new UID range. Guarded by a promise rather than a lock, because a push and a tick arriving together is normal and two passes would double the work and race on the cursor. The minute tick is still the floor — so the worst case of the whole watcher failing is the behaviour we would have had without it.

Parsemailbox/parse.ts

Headers, body, thread. Decides whether a machine wrote it.

Consequencesmailbox/consequences.ts

What needs no judgement, in a fixed order: suppression first, then stopping sequences — because stopping a sequence pulls its queued mail and suppression pulls everything else queued for that address too. This must happen even when triage is off, even with no model key, and even when every agent is paused. A sequence that keeps writing to somebody who has already answered is the exact failure this module exists to end, and it must not be contingent on an API key.

Triagemailbox/triage.ts

The only model call in the mail room, and deliberately the smallest decision in it. Four questions: what kind of letter is this (one of sixteen intents), what does it say in a sentence, how quickly does it need an answer, and how sure are you. It does not decide who gets the work and does not write a word that reaches a customer.

Routemailbox/router.ts

A table, not a judgement. Each intent has a destination for a known client and a destination for a stranger, because the same question from a stranger and from a client of two years is one question and two different jobs — one is a sale, the other is support.

Raiseagents/runner.ts

An EVENT task for the destination agent, carrying the reason in the words the Inbox screen shows.

Why the classification and the routing are separate

A model that chooses the agent is a model that can hand a complaint from a paying client to the cold-outreach writer, and no amount of prompt wording makes that reliably impossible. A model that chooses between sixteen named intents can be wrong in sixteen ways, all of which are visible on screen, and every one of which maps to a routing decision a person approved once, in advance.

The confidence floor does real work

Below 0.6 the message is labelled and given to nobody, which is the honest outcome for mail the system does not understand. An unrouted message sits on the Inbox screen for a person; a confidently misrouted one starts an agent writing to somebody about the wrong thing.

An out-of-office is not a reply

It carries Auto-Submitted, it arrives within seconds of a send, and treating it as an answer stops the sequence, marks the lead engaged, and loses the prospect in silence. Nothing acts on a message a machine wrote — except a bounce, which is read off the headers rather than off a model.

Three more rules hold the router. A retired or paused agent is not a destination — the fallback chain ends at the Mail Room itself, then at nobody, which puts the message on screen for a person, because silently handing work to an agent nobody has switched on is the same as losing it. Some letters route to nobody on purpose: a bounce, an out-of-office and a clear no have already had everything done about them that should be done, and raising a task for each would spend a model call to conclude there is nothing to do. And the Sent folder is read too, so a reply the founder typed on his phone stops the machine chasing behind him.

05.4

Outreach, and the leads with a number and no email

Outreach runs as sequences: enrol, send inside the window, stop on reply. Suppression is checked before anything goes out. The doctrine those letters are written to is the cold-email skill rather than the older playbook, and it lives in the owning agent’s process layer — which is the surface an edit actually reaches.

For a lead with a phone number and no address there are two more channels on the same dispatch tick. Both are shaped by one constraint: the 24-hour window. Outside it, WhatsApp will only carry an approved template, which is why templates are managed as first-class objects rather than composed per send. SMS has no such window and no such richness, and is treated as the fallback it is.

The demo page offer

Cold outreach can offer a free page built for that specific business. A public page carrying somebody else’s name is an outward act with a reputational edge to it, so it is guarded: the design direction is sourced rather than invented, and publishing is an outward call like any other — level 3, or a preview and a card.

05.5

Approvals — the other half of a preview

The gate has always downgraded a risky call to a preview. This is what makes approving it mean something.

Before this existed, approving a task marked it DONE and the previewed letter was never sent — so “approve” meant “I have read this” and the work still had to be done again by hand. Now an approval re-invokes the tool with the input the schema validated at proposal time, so what happens is what was shown, not a second model call that might produce something else.

1
The agent proposes
An outward or spending call comes back as a preview. An ActionRequest is filed with the exact validated input and the three-part rationale.
2
It appears where a decision can be made
The approvals queue in the app, and as a card in Slack.
3
A person decides
Approve or reject, with an optional note. Recorded against a signed-in user or a Slack user id.
4
It is carried out through the same gate
Readiness and the grant are re-checked; only the dry-run downgrade is lifted. An approval sitting in the queue after the tool was revoked is refused rather than honoured.
5
Or it expires
A week-old proposal is a re-ask, not a refusal.

Idempotency here is not a nicety

Slack retries anything it does not hear back from inside three seconds. A retried Approve that sent a second letter would be the worst possible bug in this file — the prospect gets the same email twice and the record shows one send. So the status transition is a conditional update, exactly as the task claim is.

05.6

Hiring — how the workforce grows itself

Three steps, and keeping them separate is the whole design.

1
A gap is recorded
An agent hits work outside its own craft, runs findAgent, finds nobody, and calls needSkill. That is a demand signal and nothing more.
2
A hire is proposed
The Agent Creator reads the gap, checks it is not already somebody’s job, designs the agent — all __LAYERCOUNT__ layers, with the smallest toolkit that does the job — and files a request.
3
A hire is decided
By a person clicking Approve in Slack, or by the standing policy when it is set to automatic. Only this step writes to the agent table.

No model ever creates an agent

The Agent Creator’s tool files a request. One function creates an agent, and it is reached only from a signed Slack interaction, an authenticated API call, or the automatic policy. That separation is not ceremony: an agent that could create agents directly could grant itself any tool in the catalogue by hiring a copy of itself with a wider one, and there is no prompt wording that reliably prevents that.

Every hire lands the same way — specialist tier, autonomy 1, dry run on — however it was approved. Automatic decides who exists. It never decides what they may do.

Ceiling on custom agents
25. Beyond it the Creator is refused and told to escalate.
Ceiling per rolling day
3, so a runaway loop stops at three rather than thirty.
Proposals waiting at once
5. It must stop proposing until some are decided — which is why unanswered ones have to expire.
A gap already covered
Worse than useless: it argues for hiring a duplicate.
05.7

Rehearsals — watching the whole workforce work

Point the workforce at one real website and watch what it does. It wakes the agents it needs and puts them back afterwards.

A rehearsal is three facts — a website, a scenario, and a scratch lead — and everything after that is the ordinary runtime doing what it always does. The root task carries a rehearsal marker and the runner passes it down through every hand-off and delegation, so nothing anywhere in the tree can reach outside the building. It is nudged along faster than the minute tick, because a chain of six agents at one a minute is unbearable to watch. And it can be thrown away, because a rehearsal that could not be deleted would make the second one more expensive than the first.

What a rehearsal holds back

Exactly the outward flag, and nothing else. Sending an email, enrolling a sequence, opening an issue, booking a meeting, raising a payment, publishing a page under a stranger’s name. Those stop at a preview whatever autonomy their agent is on. That is the whole of the guarantee.

What it deliberately does not

Reads, because a read has no preview and blanket dry-run would have refused every one of them — every agent blind, the timeline full of refusals, and the rehearsal a test of nothing. Writes to our own records, which land on the scratch lead. And spending: a research pass and a site audit cost real money and there is no honest way to rehearse them without paying. What the run cost is totalled on screen instead — which is worth knowing before the workforce is turned loose on four hundred leads.

Two ceilings: one task at a time for the whole rehearsal, below the process ceiling so a wide scenario cannot fill the floor and leave real work queued behind it; and 24 tasks for the whole run, which is a spending limit rather than a safety one — a scenario that delegates in a circle would otherwise be discovered on the invoice.

The one to keep an eye on is the capture tool: it spends without being outward, so a brief that talked an agent into scraping a city would really scrape it. Nothing in the shipped scenarios asks for that, and the run ceiling plus the cost readout is what would show it.

05.8

Budgets — what it may spend before it stops itself

The one part of this system that spends without anybody pressing a button — on a schedule, all night, across __AGENTCOUNT__ agents — used to be the part with nothing above it, and the only symptom of a runaway would have been an invoice at the end of the month.

50%
Warn
Say so on screen. Change nothing.
75%
Downgrade
Keep working, on the cheap model.
90%
Approve
Prepare outward and spending work; do not carry it out. Reuses the dry-run preview rather than inventing a third way for work to be held.
100%
Pause
Start nothing new. The one refusal an approval cannot lift.

The two in the middle are the point. Between them the workforce spends the last quarter of its budget doing the same work more cheaply and more carefully, rather than falling off a cliff at the end of the month. A ceiling that can only stop work is a ceiling nobody dares set low enough to be useful.

Several budgets can apply at once — a scope for the agent, for the tool, for the vendor — and the strictest wins. A missing budget is not a zero budget: nothing is enforced until a limit is set, because shipping a default ceiling would stop a working business on the day it deployed.

05.9

Model routing, and what happens when a vendor is down

The caller names the job, never the vendor. Moving every piece of writing in the system from one provider to another is a settings change rather than a diff.

__MODELJOBTABLE__

Every provider is spoken to over plain HTTP rather than an SDK — three more SDKs would be three more dependency trees and three more ways for a transitive package to break a deploy, in exchange for wrapping one POST each. The exception is Anthropic, which keeps its SDK because the agent loop needs streaming, tool use and thinking blocks.

Structured output is a contract, not a hope. All the vendors support a JSON schema on the response in three different shapes; each adapter translates the one schema the caller wrote into the shape its vendor wants, and a caller never sees the difference.

Failover, and the one failure never routed around

When the assigned model fails, the next capable one in the chain takes over. The exception is a refusal: a model declining to do something is an answer, and routing around it until somebody agrees is how a policy gets laundered. The trap that made this look healthy when it was not: a stubbed vendor that returns success makes a broken provider read green — so the harness has to assert on what came back, not on whether something came back.

05.10

Who writes what

__WRITERCOUNT__ writing jobs, each with exactly one owner. An agent may own several jobs; a job has exactly one owner.

This exists to close a specific defect. The Agents screen showed a prompt, the founder edited it, and the next cold email came out identical — because the email was never written by that prompt. It was written by a string constant no screen displayed and no edit could reach. The roster was a set of labels over a set of hard-coded writers. The doctrine was in two places at once, and the editable one was not the one that ran.

__WRITERTABLE__

Two owners for one deliverable would be the contradiction that makes a model fall back to the generic output it already knew, which is why the rule runs one direction only.

06.2

What is on, and what a person still decides

Running by itself

Lead capture on schedule. Webhook intake. The mailbox, read live and on the tick, including Sent. Suppression and sequence-stopping. Sequence advance. Care-plan billing. Standing work. Task execution, resume and reaping. Housekeeping. Budget thresholds. Model failover.

Waiting for a person

Every outward act at the shipped settings — each email, each enrolment, each published page, each payment link. Every hire. Any autonomy level above 1. Any budget ceiling, since none is enforced until one is set. And every message triage was not confident about.

Two things that make a refusal test lie

The no-auth development mode means every request arrives as the Owner, and an Owner-driven call skips the grant and autonomy checks entirely. A permissions test that passes there has proved nothing. And an unset budget is not a zero budget — a ceiling that was never configured does not refuse anything, so “the budget did not stop it” is usually the honest answer that no budget existed.

Still to be connected

Everything below is coded, gated and inert until a value is pasted into Settings, where it is encrypted at rest. None of it needs a redeploy. A tool whose integration is unconfigured is refused at the first check with a sentence that names the setting — which is the whole reason readiness is checked before anything else.

The Google connection is the one exception worth flagging: the calendar tools need no new key, but an older refresh token does not carry the calendar scopes, so the connection has to be redone rather than topped up.
